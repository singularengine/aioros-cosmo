# Working on this repository

Guidance for every agent and person working on Aioros.Cosmo, the UI component library of Aioros: shadcn/ui's
components, variants and design tokens as pure Avalonia XAML, served as HTML by Aioros on the web and drawn natively by
Avalonia on the desktop. It follows Aioros's rules (`aioros/AGENTS.md`, `aioros/docs/principles.md`), adapted to a
library that ports shadcn/ui. The rules are enforced by the architecture tests and the analyzers wherever they can be.

## Before you change anything

1. Read the [README](README.md), the [roadmap](docs/roadmap.md) and the [coverage](docs/coverage.md).
2. Build and test. Both must be green before and after your change, in Debug and in Release. The machine may be shared:
   build with `-m:4`. The browser tests need Chromium (`/usr/bin/chromium`, or the path in `CHROMIUM`).
3. Do not reinvent and do not assume. The reference is shadcn/ui's source at the commit pinned in `tools/shadcn`
   (new-york-v4): read the component you port (`tools/shadcn/registry/ui`), port its classes value for value, and compare
   the result with shadcn/ui's own render (`tools/shadcn/out`, written by `tools/shadcn/capture.mjs`). Note any divergence
   and its reason in its acceptance criterion.
4. When a component needs something Aioros cannot express on the web, do not work around it: write the precise need in an issue on Aioros, with the place in it and the visible effect.

```
dotnet build Aioros.Cosmo.slnx -m:4
dotnet test --solution Aioros.Cosmo.slnx
```

The SDK is Aioros's (`global.json`, 10.0.403): link Aioros's repository-local SDK with
`ln -s ../aioros/.dotnet .dotnet` or install it there with `eng/install-sdk.sh`. CI's `dependencies` workflow fails when that
SDK lags a security release of .NET or a package has a known advisory (`eng/check-dependencies.py`, as Aioros's). Aioros and Aioros.Pictor come from nuget.org.
npm is used only inside `tools/` folders (`tools/shadcn`), and `node_modules` is never committed.

## Adding a component

1. Read shadcn/ui's source for it (`tools/shadcn/registry/ui/<name>.tsx`) and its examples, and how Avalonia and the web
   do the same natively (prefer Avalonia's own control and the native HTML element Aioros writes for it).
2. Add its fixtures to the reference app (`tools/shadcn/app/src/fixtures.tsx`) and capture them
   (`npm run build && node capture.mjs` in `tools/shadcn`).
3. Write its criteria in `docs/acceptance/<name>.md`, after checking that no criterion covers it already: its looks
   against the reference (light and dark, rest, hover, focus, disabled), its boxes, its behavior under mouse, touch and
   keyboard, its accessibility, and **its XAML features** (below).
4. Write the tests (`tests/Aioros.Cosmo.Tests` on the desktop, `tests/Aioros.Cosmo.Gallery.Tests` on the web), watch
   them fail, then write the control theme, its tokens (`tools/shadcn/tokens.mjs` for derived brushes) and, only where
   Avalonia has no control, a sealed control.
5. Show it in the Gallery: a page under `samples/Gallery/Gallery/Pages/components/<name>` (generated by
   `samples/Gallery/tools/pages.py`, so each example's code is the XAML it renders) and its fixtures under
   `Pages/fidelity/`.
6. Update [docs/coverage.md](docs/coverage.md) (its row, its features, its fidelity matrix row and the counts) and
   [docs/fidelity.md](docs/fidelity.md) (`node tools/shadcn/compare.mjs`).

## XAML features are first class

Every component supports, on both targets, out of the box: data binding on every public property (one way, and two
way where the property is an input: a switch's `IsChecked`, an input's `Text`, a select's `SelectedItem` and
`SelectedValue`), value converters (custom and Avalonia's built-in ones, `BoolConverters`, `ObjectConverters`,
`StringConverters`, `StringFormat`), commands (`ICommand`, `CommandParameter` and `CanExecute` on anything clickable),
`DataTemplate`s (`ContentTemplate`, `ItemTemplate`) wherever content is involved, styles, control themes and resources,
compiled bindings (`x:DataType`), and MVVM with no code-behind. Each component's criteria cover them (see
`docs/acceptance/binding.md`) and the Gallery's `/binding` page shows them. If Aioros's web plan cannot follow a bound
property or a converter for a Cosmo control, open an issue on Aioros instead of working around it.

## Writing tests

Tests come before the code they verify.

1. **Write the acceptance criteria first**, in the area's file in [docs/acceptance](docs/acceptance), as a table row
   `| AREA-NN | criterion |`. The identifier is never reused. Each criterion describes one observable behavior in
   Given / When / Then form, names the expected outcome precisely, and covers the rejected paths too.
2. **Check for duplicates** in the acceptance files and the tests; extend an existing test instead of adding one.
3. **One test per criterion**, carrying it: `[Trait("AC", "BUTTON-01")]`. The architecture tests fail on a criterion
   without exactly one test and on a test without exactly one known criterion. The test name states the behavior in
   PascalCase, with the `Async` suffix for asynchronous tests.
4. Write the test first and watch it fail, then write the code.
5. No sleeps, no waits on time: await the signal that states the thing happened (a selector, a process's exit, a page's
   answer). Prove a new rule can fail: break it on purpose, watch the test fail, restore it.

## Architecture

- `src/Aioros.Cosmo` is the library: control themes, styles, resource dictionaries and small sealed controls. It
  references **Avalonia and Aioros.Markup only** (Aioros.Markup holds the `a:Web.*` hints and references Avalonia
  only; no Aioros engine, no ASP.NET Core), so it runs in any Aioros app and in a plain Avalonia app.
- The tokens are generated (`tools/shadcn/tokens.mjs`) from the pinned registry; never edit
  `src/Aioros.Cosmo/Theming/Colors`, `Radius` or `TokenDictionaries.cs` by hand.
- **Composition over inheritance.** Every class and record class is `sealed` or `static`.
- **No locks, no concurrent collections, no reflection** in `src/`.
- **Performance is the point.** A component is control themes and resources; prefer what Aioros plans (classes,
  bound classes, theme variants, resource dictionaries) to anything that sends a page to the engine. Measure with the
  method of [docs/benchmarks.md](docs/benchmarks.md).
- **Screaming architecture.** Folders and namespaces name what the code does: `Theming`, `Buttons`, `Display`…

## Code

- Modern C# 14 on .NET 10. The smallest code that states the behavior clearly.
- No comments. XML documentation on the public API only (required: the library generates documentation).
- No type longer than 600 lines; Sonar's cognitive complexity (15), nesting (3) and method length (80) limits apply.
- Warnings are errors.

## Documentation

- Everything in the repository is written in English.
- Update the coverage and the roadmap in the same change when they change, and keep THIRD-PARTY-NOTICES.md in step with what is ported.
